People & Names

A roster, a dossier, and the same judgement rendered into the scroll where you will actually read it.

Why a database at all

The name database knows who is an enemy. That is worth very little if reading it means typing a command — the moment it matters is the moment a name goes past in a room description or a shout, and you have about a second. So the database is rendered into the game text itself: known names take on colour and weight in place.

Everything else here exists to fill that database honestly. A roster built from guesses would colour an ally red once and never be trusted again.

Standing: declared and derived

Two independent mechanisms, and declaration always wins.

SourceHow it is set
Declaredemset iff <person> ally|enemy|auto. Survives an import, and survives the derived rules changing under it.
DerivedFrom city, house and order hostility — lua emunah.namedb.setHostile("city", "Mhaldor", true) marks every recorded Mhaldorian an enemy without touching a single record.

auto hands the decision back to derivation. The distinction matters because the derived rules are broad by design: an org-wide marking is the efficient way to express a war, and an explicit exception is the way to express the person inside it you are not fighting.

Highlighting: colour and weight

Two channels doing two different jobs, and keeping them separate is the whole point.

ChannelAnswers
ColourWhere do they stand relative to me — enemy, ally, or which city.
WeightIs there something about this person — a Dragon, a Mark, infamy, or an importance you set yourself.

They stack. A Mhaldorian Dragon who is also enemied to your city reads as enemy-red and bold and underlined, and each of those three is independently recoverable by eye. A scheme that folded them into one colour ramp would make the common case (an ordinary citizen of a hostile city) and the rare one (a Dragon Mark) look alike, which is the opposite of what a highlighter is for.

A candidate is only ever styled if it is already a record. Nothing is ever invented from a capitalised noun at the start of a sentence. Your own name is never highlighted — it is on almost every line worth reading, and marking it turns the signal into noise.

The opt-out

lua emunah.ui.names.ignore("<person>", true), for the ally whose name is a common word or the shopkeeper you see forty times an hour. It forgets nothing else about them.

The highlighter used to run on nearly every line

Its trigger was [A-Z][a-z] — "contains a capitalised word" — on the reasoning that this is the cheapest pre-filter Mudlet can apply. Both halves of that were true and the conclusion was still wrong, because the pre-filter did not filter: in Achaea essentially every line contains a capitalised word. Measured, it matched 88% of lines, each costing a full database scan.

The trigger is now built from the roster itself — one alternation regex, rebuilt when the database changes — and fires on 12% of lines, which is the lines that actually name somebody. See Performance.

Where records come from

GMCP names people exactly, which is why it is the only fully automatic source. Everyone who walks into the room and everyone who speaks gets a record; neither says anything about allegiance, so neither ever sets a relationship.

The game-text listings fill in the rest:

SourceWhat it gives
CWCity roster: name, rank, city.
CLWHOClan membership.
QWWho is nearby. Has no header line, so it is read backwards from its terminator — the walk stops at the first line that is not a comma-separated list of capitalised words, which is what makes it safe without one.
HONOURSThe richest single source: full name, sex, race, city, house, order, level, and more. Its header alone is a weak signature, so it only arms a candidate that the rule of dashes on the next line has to confirm.
Guardian angelLocation and health for a named person. The most perishable and most actionable thing the database holds.

The namedb.capture setting switches these sources off, and emset debug shows what each has produced, which is how you tell "not implemented" from "never seen one".

The Achaea web API

namedb/api.lua reads api.achaea.com/characters/<name>.json, which is how emset whois can answer for someone never seen in play. Observed behaviour, from docs/game/api.md:

  • Every value is a string, including the numeric ones.
  • mob_kills is sometimes abbreviated — "451k", which tonumber reads as 451. The single most dangerous field in the payload, and the reason it is stored as text.
  • A missing character returns 403, not 404.
  • city, house and class come back lowercase; "(none)" means absent.
Self-imposed rate limiting

The endpoint sends no rate-limit headers, so the limit is unknown and finding it experimentally seemed unwise. Requests are serialised through a one-per-second queue, hits are cached for six hours and misses for twenty-four. A timeout is deliberately not cached — that is a network problem, not an answer.

Export and import

emunah.namedb.exportFile(path, opts) writes the database out; with opts.fields writes a subset, with notes excluded because those are yours. emunah.namedb.importFile(path) merges someone else's in.

Import is additive on purpose. Someone else's file is evidence about people you have not met, not a correction of the judgement you have already recorded about people you have — so your own iff and your own notes survive a merge intact.

emunah.namedb.forgetAll() clears it. emunah.namedb.prune(days) drops records that are only a name; anything declared, noted, or given a single fact by hand survives, so it can never quietly discard judgement.

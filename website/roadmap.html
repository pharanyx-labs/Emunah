Roadmap

GMCP tracking, the curing engine and the hunting loop are complete and covered by tests. Two structural gaps separate the current state from a system that holds up in player combat. This page records both, what is planned around them, and the principles that decide what ships.

The gaps

Offence is single-attack

class/priest.lua issues one attack command and implements handleShield as an explicit refusal rather than a guess. There is no affliction sequencing, and only one class is implemented.

The trigger corpus is small — and that matters less than it did

This used to be the headline gap, on the reasoning that Char.Afflictions reports only what Achaea chooses to announce and is therefore unusable for PvP. That reasoning was wrong, and finding out cost less than acting on it would have.

GMCP can be relied on for every affliction in PvP except loki and blackout, with recklessness as a third case that falsifies vitals rather than hiding afflictions. DIAG answers loki, and curing/detect/diag.lua ships that. So the corpus is no longer the thing standing between the system and player combat; it is an optimisation — cure-side patterns free a vector a round trip earlier than the fallback timer would.

What that changed

The plan had been to grow a few hundred onset patterns from sparring transcripts before PvP could be trusted at all. Most of that work is now unnecessary. It is recorded here rather than quietly deleted because the reversal is the useful part: the assumption was plausible, load-bearing, held for months, and never checked against the game.

Planned

Offensive sequencing

A lock-sequencing table shaped like the existing cure convention, gated on opponent affliction state. Blocked on detection: sequencing against an opponent model that cannot see afflictions is guesswork.

A second class

Monk, which needs no adapter changes. A second implementation is the only way to confirm the sequencing logic is not accidentally Priest-specific. A guide to adding a class follows the second one, not the first.

Shield handling

Unimplemented until a shield-break mechanic is confirmed in play. The hunting loop treats the refusal as "cannot handle this" and stops, which is correct for an unknown.

Tattoo keep-up

Defences raised by touching a tattoo — boar, moss — rather than by a skill. The mechanism already exists: emset defs add <name> <command> supplies the raising command, and the grid shows [-] for a defence wanted with no command available. What is missing is the shipped set.

CON-based difficulty

Using a denizen's CON to decide whether it is worth attacking, and whether the health floor should be higher for it. Blocked on confirming what the values actually mean in play.

Open data questions

Six items need in-game confirmation, most significantly whether five table entries are defences mismodelled as afflictions.

Working principles

These are why the roadmap has fewer items than it might.

A wrong assertion is worse than a gap. A missing pattern is inert. A wrong one asserts an affliction the character does not have, and the engine spends a balance curing it. Where the exact game text or mechanic is unknown, the feature waits rather than shipping on an assumption.

Evidence over reasoning. Mechanics are established from timestamped transcripts and GMCP traces, not from what the game plausibly ought to do.

Every behavioural fix carries a regression test that would have caught the original report, and the suite is green before anything is committed.

See Curing → Detection for the workflow this roadmap depends on, or Curing → How the cure data is verified for data provenance.

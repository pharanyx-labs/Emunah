Roadmap

GMCP tracking, the curing engine and the hunting loop are complete and covered by tests. Two structural gaps separate the current state from a system that holds up in player combat. This page records both, what is planned around them, and the principles that decide what ships.

The two gaps

Affliction detection is GMCP-driven

The trigger framework in src/emunah/curing/detect/ is complete and data-driven. Its corpus is deliberately small, because Char.Afflictions reports only what Achaea chooses to announce — sufficient for hunting, incomplete for player combat by design.

Closing it requires real message text, which cannot be written from documentation. Achaea's published help supplies affliction names, cure vocabulary and the class structure, but no message wording, balance figures or stacking rules. It serves as a completeness checklist, not a pattern source.

The workflow is emunah learn on, fight or spar, emunah learn off, then add what was observed. In priority order:

  1. Onset detection for the blocking afflictions: anorexia, asthma, slickness, paralysis.
  2. Cure-side confirmation for the writhe-class binds.
  3. Common lock-setup afflictions, named from the checklist, worded from transcripts.
  4. The long tail, driven by what curing actually needs.
Why hunting transcripts have not closed this

Combat logs gathered so far have been productive, but for mechanics rather than afflictions: balance behaviour, knockdown and stun handling, rejection wording, healing costs. None has produced an affliction onset message, because hunting denizens does not afflict the character. The corpus needs sparring or player combat specifically — the afflictions above are ones another player applies deliberately, and no amount of PvE logging will surface them.

Offence is single-attack

class/priest.lua issues one attack command and implements handleShield as an explicit refusal rather than a guess. There is no affliction sequencing, and only one class is implemented.

Planned

Offensive sequencing

A lock-sequencing table shaped like the existing cure convention, gated on opponent affliction state. Blocked on detection: sequencing against an opponent model that cannot see afflictions is guesswork.

A second class

Monk, which needs no adapter changes. A second implementation is the only way to confirm the sequencing logic is not accidentally Priest-specific. A guide to adding a class follows the second one, not the first.

Shield handling

Unimplemented until a shield-break mechanic is confirmed in play. The hunting loop treats the refusal as "cannot handle this" and stops, which is correct for an unknown.

Open data questions

Seven items need in-game confirmation, most significantly whether five table entries are defences mismodelled as afflictions.

Working principles

These are why the roadmap has fewer items than it might.

A wrong assertion is worse than a gap. A missing pattern is inert. A wrong one asserts an affliction the character does not have, and the engine spends a balance curing it. Where the exact game text or mechanic is unknown, the feature waits rather than shipping on an assumption.

Evidence over reasoning. Mechanics are established from timestamped transcripts and GMCP traces, not from what the game plausibly ought to do.

Every behavioural fix carries a regression test that would have caught the original report, and the suite is green before anything is committed.

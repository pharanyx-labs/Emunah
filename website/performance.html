Performance

Achaea combat is decided on round trips. A cure that resolves after the prompt it was needed on is a cure that did not happen. Mudlet runs every installed package in a single Lua state on the UI thread, so time spent here is time the whole client is not drawing, not reading input, and not sending.

This page records what the hot paths are, what was wrong with them, and how to measure whether a change made things better. It is not a style guide. Everything below was measured, not reasoned about — see docs/performance.md in the repository for the source this page is generated from.

The four paths that matter

PathFires onCost
Trigger matchingEvery line of game outputMudlet C++ PCRE — free to us
Trigger callbacksEvery line whose pattern matchedAll of it ours
engine.tick()Every prompt (Char.Vitals)All of it ours
UI repaintsEvery prompt, and every item/affliction/defence eventAll of it ours, and Qt's
This page used to say the per-line path needed no attention

It asserted: “there is no Lua handler on sysDataReceived and there must not be one.” Literally true, and it missed the point. A tempRegexTrigger whose pattern matches every line is a per-line Lua handler with extra steps — Mudlet still runs the callback in Lua once the C++ matcher fires. There were five such triggers; see the name-highlighter finding below.

What it costs now

Measured with test/bench.lua under a realistic lock: eight afflictions tracked across every vector, herbs in hand, health and mana below all four healing thresholds.

The line and chyron rows are the ones that were invisible to per-tick benchmarking before — and between them they are worth more than the tick itself.

A note on the byte column

Earlier measurements quoted figures like “292 bytes per tick.” Those were wrong — not by a little. The collector was running during the measured loop, so the delta was “allocated minus whatever happened to be collected,” which varied between 194 and 732 bytes per call across consecutive runs of identical code. The collector is now stopped for the measured loop; the honest figure for a tick is 2037 bytes, not 292. Do not compare a byte figure measured with the collector running against one measured without it.

What was wrong

Ordered by what it was actually costing.

1. The name highlighter ran on nearly every line

ui/names.lua registered [A-Z][a-z] — “contains a capitalised word” — reasoning that it was the cheapest possible pre-filter. True, and the conclusion was still wrong, because the pre-filter did not filter: in Achaea, nearly every line of room description, combat text and channel output contains a capitalised word. Measured over eight representative lines it matched 88% of them, and each match ran a name-table walk costing roughly 21 µs at a populated roster.

The trigger is now built from the roster itself — one alternation regex, rebuilt only when the name database changes — and the callback now fires on 12% of lines: the lines that actually name somebody.

2. The chyron allocated ~140 strings a second

ui/chyron.lua re-rendered at 12.5 Hz for as long as any message was up, independent of prompts and invisible to every tick benchmark — rebuilding the scroll and walking it one character at a time on every step. None of that depends on the scroll position. The reel is now compiled once per message change into a byte-offset index and a per-glyph colour; a step is one sub() call and one concatenation.

3. Re-normalising names that were already normalised

The curing engine lowercases a tracked name once, on the way in — and several lookup functions then lowercased it again on every read, about 164 times per prompt. Each of them now tries the bare key first and normalises only on a miss.

4. Asking vector-independent questions once per vector

The resolve loop ran once per balance vector and re-asked three vector-independent questions about the same tracked afflictions each time. They are now asked once per tick and the per-vector loop reads the cached answer — cutting one of them from 53 calls a prompt to 8.

5. Panels repainting when nothing had changed, one row at a time

No panel used a dirty flag, and each issued one draw call per row rather than one for the whole panel. Panels now build their entire body and issue a single draw call, skip the draw entirely when the body is byte-identical to what is displayed, and restyle only the specific elements that changed.

6. Smaller things, each real

  • A hex-colour helper parsed and reformatted on every call instead of once at load.
  • A rift lookup fell back to a linear scan on the common query shape instead of an alias index.
  • A defence-block check walked a nested table instead of a reverse index built once.
  • A capture buffer shifted its whole contents on every line instead of using a ring cursor.
  • Vitals parsing allocated fresh tables on every prompt instead of filling in place.
  • An item-attribute parser ran fourteen string searches per item per repaint instead of caching the result.

Measuring

lua test/bench.lua [iterations]     # wall time and bytes per call
lua test/profile.lua [iterations]   # sampling profiler, hottest lines
lua test/run.lua                    # includes the draw-call budget assertions

Four traps, all of which produced confidently wrong numbers before they were noticed:

os.clock is stubbed

The test mock replaces it with a manually-advanced clock so cooldown maths is deterministic. Timing against it measures the fake clock, not wall time — use the mock's real-clock escape hatch for benchmarking.

The profiler's own timings are meaningless

A sampling hook at a fixed instruction interval dominates the wall clock. Its relative sample counts are what to read; take absolute figures from bench.lua, which runs unhooked.

The collector must be stopped to measure allocation

See the byte-column note above. bench() does this automatically; anything measuring bytes by hand must too.

Per-line and UI costs cannot be timed through the mock

The test mock matches triggers and issues draws in ways that are nothing like Mudlet's real cost. Both are measured as counts instead — how many callbacks a line provokes, how many draw calls a repaint issues — since the count is what transfers to Mudlet even though the time does not.

Rules for changes

  • A trigger pattern that matches most lines is a per-line Lua handler. Before adding a tempRegexTrigger, ask what fraction of real output it matches. If the answer is “most,” narrow it or drive it from data.
  • Nothing per-line in Lua that a pattern could have excluded.
  • Cache against a generation, not a timestamp. A time-based cache in a curing system is a stale-state bug waiting for a fight to expose it. Bump a counter at the mutation site.
  • Every memo needs an invalidation test, written to prime the cache first.
  • Prefer a shared read-only constant to a fresh empty table, and never hand one to something that mutates.
  • A panel draws once, or not at all. One draw call per repaint, none when the rendered body is unchanged.
  • Measure before and after, and check the metric is real. Most of the traps above were found by a number that looked plausible.
Everything on this page was measured, not reasoned about. The benchmark and profiler live in test/bench.lua and test/profile.lua; the draw-call budget is asserted in test/run.lua.
